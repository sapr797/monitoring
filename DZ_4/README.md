Первопричина (Root Cause)
Короткая (43 секунды) потеря связи между сетевым хабом и дата-центром на восточном побережье США привела к каскадному отказу, вызванному поведением Orchestrator – системы управления MySQL-кластерами. Orchestrator, сконфигурированный на основе алгоритма Raft, начал процедуру перевыбора лидера. Узлы на западном побережье и в облаке смогли сформировать кворум и инициировали кросс-региональное переключение мастеров (с востока на запад).

При этом:

Приложения GitHub были не рассчитаны на работу с мастерами БД на другом конце страны (высокая задержка).

За время, пока связь была потеряна (43 секунды), восточный кластер успел принять небольшое количество записей, которые не реплицировались на запад.

После восстановления соединения оба кластера содержали записи, отсутствующие в другом → классическая ситуация «расходящихся историй» (divergent histories), что сделало невозможным автоматический фейловер обратно.

Техническая причина: Orchestrator был настроен на возможность межрегионального продвижения мастеров, хотя приложения этого не поддерживали. Раньше такая ситуация не возникала из-за отсутствия столь серьёзного сетевого разрыва.

Воздействие (Impact)
Пользователи: 24 часа сайт был недоступен или работал с серьёзными проблемами (несогласованные данные, неработающие веб-хуки, Pages).

Бизнес-последствия: подрыв доверия к надёжности GitHub (компания принесла публичные извинения).

Данные: никто не потерял данные, но несколько сотен записей (например, 954 записи в одном из самых загруженных кластеров) потребовали ручного анализа и возможного вмешательства.

Внутренние процессы: задержка публикации блога из-за собственного отказа Pages, неточные прогнозы по времени восстановления.

Действия, предпринятые во время инцидента
Приоритизация целостности данных перед доступностью и скоростью восстановления.

Остановка некритичных фоновых задач (веб-хуки, Pages) для снижения нагрузки.

Восстановление кластеров из резервных копий (хранятся каждые 4 часа в облаке). Это заняло много часов из-за большого объёма данных (терабайты) и ограничений скорости загрузки.

Добавление дополнительных read-реплик в облаке для распределения нагрузки.

Ручная обработка бэклога (5 млн веб-хуков, 80 тыс. сборок Pages).

Увеличение TTL для веб-хуков, чтобы избежать дальнейшей потери событий.

Меры, принятые после инцидента (для предотвращения повторения)
Технические инициативы
Изменение конфигурации Orchestrator – запретить продвижение мастеров БД между регионами. Переключение допустимо только внутри одного дата-центра.

Ускорение миграции на новую систему статусов – вместо «зелёный/жёлтый/красный» предоставлять детальную информацию о состоянии каждого компонента.

Активная/активная/активная архитектура (multi‑datacenter active/active/active) – проект, начатый до инцидента, получил приоритет. Позволит выдерживать отказ целого дата-центра без влияния на пользователей.

Тестирование предположений (Fault Injection / Chaos Engineering) – систематическое внедрение сбоев в тестовой среде, чтобы выявлять слабые места до того, как они повлияют на продакшен.

Организационные изменения
Сдвиг мышления в сторону надежности – переход от простого усиления контроля и ускорения реакции к проактивному валидированию сценариев отказов.

Улучшение коммуникации – более точные прогнозы времени восстановления, публикация обновлений даже при отказе собственных инструментов (например, Pages).

Извлечённые уроки (Lessons Learned)
Короткий сетевой сбой (43 секунды) может вызвать многочасовую деградацию, если система управления БД не учитывает ограничения приложений.

Распределённые системы должны быть спроектированы с учётом возможных задержек и расходящихся состояний. Автоматический фейловер между регионами опасен без механизмов разрешения конфликтов.

Приоритет целостности данных – правильное, но дорогое решение (24 часа простоя). Необходимы более быстрые методы восстановления (например, реплики с отложенной синхронизацией).

Точность прогнозов времени восстановления крайне важна для доверия пользователей. В данном случае команда ошиблась, экстраполируя линейное уменьшение задержки, тогда как реальный процесс следовал степенному закону (power decay).

Собственная инфраструктура GitHub (дата-центры, не облако) накладывает ограничения на скорость восстановления из бэкапов (терабайты данных передаются по сети).

Chaos Engineering помогает выявить подобные «эмерджентные» поведения, которые не видны при штатной работе.

Вывод
Инцидент 21–22 октября 2018 года стал для GitHub важным уроком о том, что даже плановое обслуживание одного сетевого компонента может привести к катастрофическому отказу из-за неучтённых взаимодействий между системами (Orchestrator + приложения). Компания публично признала ошибки, извинилась перед пользователями и запустила ряд технических и организационных изменений, включая переход к активной/активной архитектуре и внедрение chaos engineering. Постмортем такого уровня детализации служит примером прозрачности и системного подхода к инцидент-менеджменту.

Примечание: Восстановление всех данных было подтверждено, ручная сверка затронула лишь очень малую часть записей (менее 1000 на самый нагруженный кластер). GitHub также пообещал улучшить статусную страницу и прогнозы времени восстановления.
